# `ValueRef` shape and exposure (D1)

**Status:** decision recorded for Phase 2 of the structured-output refactor.

**Decision:** expose `ValueRef` directly through the new `run_to_value()` / `exec_program_to_value()` signatures. Document the single-threaded constraint. Do not introduce a separate owned `Value` boundary type in Phase 2.

---

## Concrete type definition

`crates/runtime/src/api/kcl.rs:87–92`:

```rust
#[repr(C)]
#[allow(non_camel_case_types)]
#[derive(Clone, Debug)]
pub struct ValueRef {
    pub rc: Rc<RefCell<Value>>,
}
```

`Value` itself (line 202–216) is a flat algebraic enum: `undefined`, `none`, `bool_value(bool)`, `int_value(i64)`, `float_value(f64)`, `str_value(String)`, `list_value(Box<ListValue>)`, `dict_value(Box<DictValue>)`, `schema_value(Box<SchemaValue>)`, `func_value(Box<FuncValue>)`, `unit_value(f64, i64, String)`.

All variants own their data via `String`/`Box`/`Vec`. The recursive types (`ListValue.values`, `DictValue.values`, `SchemaValue.config`, etc.) hold child `ValueRef`s — so the tree is `Rc`-shared all the way down.

## Send / Sync

**Not `Send`, not `Sync`.**

- `Rc<T>` is `!Send` and `!Sync` (single-threaded reference counting).
- `RefCell<T>` is `!Sync` (single-threaded interior mutability).

Even disregarding `Rc`, the inner `Value` enum contains things like `FuncValue::fn_ptr: u64` which are raw function pointers tied to the originating runtime — there is no general meaning of "send a `FuncValue` to another thread".

**Implication for the embedding API:** `Embedded` and `EmbeddedReady` are `!Send`/`!Sync`. Consumers that want parallel evaluation construct an `Embedded` per thread. Concurrent evaluation from a shared `EmbeddedReady` is out of scope for v1.

## Interior mutability surface

The `rc` field is `pub`. Any holder of a `ValueRef` can call `self.rc.borrow_mut()` and mutate the inner `Value`. This is by design — the evaluator constructs values incrementally (e.g. building up a dict during schema attribute resolution) without re-allocating, so mutation through `Rc<RefCell<...>>` is on the hot path.

For external consumers, the surface is wider than ideal, but:

- Downstream code generated by `kcl-rust-codegen` (Phase 4) does `TryFrom<&ValueRef>` immediately and discards the `ValueRef`; it never holds one alongside a mutating evaluator.
- Documented contract for the embedding API: callers must not mutate `ValueRef`s after evaluation returns. Mutation invariants are evaluator-internal.

If consumer footguns become a real problem (e.g. some downstream library starts mutating tree-shared values), a `#[non_exhaustive]`-style wrapper is the future-evolution path.

## Context dependence

**ValueRef tree data is self-contained.** Walking the tree, reading field values, matching variants — none of this requires a live `Context`. The data is owned by the `Rc<RefCell<Value>>` allocations and the inner `Value` enum variants.

What *does* require a `Context`:

- **Serialisation**: `ValueRef::plan(&Context) -> (String, String)` (`crates/runtime/src/value/val_plan.rs:234`) needs `ctx.plan_opts` for sort_keys / show_hidden / disable_none / include_schema_type_path / query_paths.
- **Raw-pointer registration**: `ValueRef::into_raw(&mut Context)` (`crates/runtime/src/api/kcl.rs:189`) registers the pointer in `Context::objects: IndexSet<usize>` for C-ABI lifetime tracking. Pure-Rust consumers do not call this.
- **GC of C-handed-out pointers**: when `Context` drops, its `objects` table is walked and registered pointers are deleted. This only affects pointers handed to C via `into_raw`; Rust-side `ValueRef`s remain valid because the `Rc` keeps the allocation alive.

**SchemaValue self-containment** (`crates/runtime/src/api/kcl.rs:238–255`):

```rust
pub struct SchemaValue {
    pub name: String,        // owned
    pub pkgpath: String,     // owned
    pub config: Box<DictValue>,            // owned, recursive
    pub config_keys: Vec<String>,          // owned
    pub config_meta: ValueRef,             // recursive
    pub optional_mapping: ValueRef,        // recursive
    pub args: ValueRef,                    // recursive
    pub kwargs: ValueRef,                  // recursive
}
```

`name + pkgpath` are sufficient to identify the schema definition. The `optional_mapping` ValueRef captures which fields are required vs optional. Consumers do *not* need access to `Context::all_schemas` to interpret a schema instance — the instance carries its own metadata. Good.

`Context::instances` (`IndexMap<String, IndexMap<String, Vec<ValueRef>>>`) is a *registry* — the same instances are reachable via tree walking from the top-level result, plus auxiliary lookup-by-type indices. It is not a hidden coupling that ValueRef holders depend on.

## `ValueRef::str` ownership (already answered)

`crates/runtime/src/value/val.rs:32`:

```rust
pub fn str(v: &str) -> Self {
    Self::from(Value::str_value(v.to_string()))
}
```

Copies the `&str` argument into an owned `String` inside `Value::str_value`. The returned `ValueRef` does not borrow into the caller's storage. This was the load-bearing answer for Phase 2.5's plan to refactor `kcl_value_plan_to_json/yaml`: returning `ValueRef::str(&local_json_string)` is safe; the function does not need the `&local` to outlive the call.

## `FuncValue` is the bear trap

`FuncValue` (line 264–275) holds:

- `fn_ptr: u64` and `check_fn_ptr: u64` — raw function pointers as integers, historically pointing at LLVM-JIT-compiled code. In the current tree-walker these are probably unused or zero for KCL-defined functions and meaningful only for plugin functions.
- `closure: ValueRef` — recursive, fine.
- `proxy: Option<Index>` — `generational_arena::Index` into runtime-side proxy function table (in the evaluator). Outliving the evaluator invalidates this.

**A ValueRef whose tree contains a `func_value` is *not* safely outliveable past its originating evaluator.** The function pointers and proxy index dangle.

**Mitigation for the embedding/codegen path:** the value tree returned by `Evaluator::run_to_value()` represents the *result* of evaluation — KCL configs, dicts, schema instances containing data. Functions in KCL are evaluation-time values: lambdas live in scope, they get called to produce other values, they don't typically end up in the result tree.

For Tilley's schemas in particular (`tilley/src/schemas/`): no helpers produce function-valued result fields. The `helpers.k` lambdas are called from schema initialisers to compute values; the resulting schema instance carries the computed values, not the lambdas.

If a future consumer surfaces functions in the result tree, the codegen layer should refuse to generate Rust types for those fields (codegen-time error rather than runtime UB).

## Concrete signatures for Phase 2

Based on the above:

```rust
// crates/evaluator/src/lib.rs
impl<'ctx> Evaluator<'ctx> {
    pub fn run_to_value(&self) -> Result<ValueRef> { ... }

    // Existing run() remains; refactored internally to share
    // plan_globals_to_value() with run_to_value().
    pub fn run(&self) -> Result<(String, String)> { ... }
}

// crates/runner/src/runner.rs
pub struct ExecProgramValueResult {
    pub value: ValueRef,
    pub log_message: String,
    pub err_message: String,
}

impl FastRunner {
    pub fn run_to_value(
        &self,
        program: &ast::Program,
        args: &ExecProgramArgs,
    ) -> Result<ExecProgramValueResult> { ... }
}

// crates/api/src/service/service_impl.rs
impl KclvmServiceImpl {
    pub fn exec_program_to_value(
        &self,
        args: &ExecProgramArgs,
    ) -> Result<ExecProgramValueResult> { ... }
}
```

`ExecProgramValueResult::value` is the structured tree. Lifetime: tied to the underlying `Rc` graph; can outlive the originating `Evaluator`/`Context` as long as no `FuncValue` is in the tree (which holds for normal config-emission workloads).

## What this *doesn't* commit us to

- Exposing `ValueRef` via the protobuf-RPC surface for cross-language consumers. The protobuf wire format and Go binding stay on the string path indefinitely (per D2).
- A separate `kcl_embed::Value` newtype wrapping `ValueRef`. If it becomes useful later (e.g. to constrain interior mutability), introducing it is a non-breaking addition because the embedding API in Phase 3 wraps `ValueRef` inside `EvaluateOutcome` — the field type can change in a future minor version with codegen regenerated.
- Any thread-safety guarantee. Single-threaded forever, unless someone produces a credible plan for parallel evaluation that handles the `Rc`/`RefCell` problem.
